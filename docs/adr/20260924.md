# ADR 2026-09-24: OPUSパイプラインのフレーム長・Oggページ構成の見直し方針

## Status

Proposed

## Context

[docs/adr/20260923.md](20260923.md)で実装したOPUS対応パイプラインは、
`PCMFrameBufferNode`のフレーム長20ms、1 Opusパケット=1フレーム、
1 Oggページ=1パケットという最もシンプルな構成になっている
([PCMFrameBufferNode.swift](../../iOS/google_stt_grpc/google_stt_grpc/Feature/Audio/Node/PCMFrameBufferNode.swift)、
[OpusEncoderNode.swift](../../iOS/google_stt_grpc/google_stt_grpc/Feature/Audio/Node/OpusEncoderNode.swift)、
[OggMuxerNode.swift](../../iOS/google_stt_grpc/google_stt_grpc/Feature/Audio/Node/OggMuxerNode.swift))。

このLINEAR16(16kHz, 16bit, mono)からのデータ量削減効果を計算したところ、
以下のことが分かった。

- LINEAR16: `16000Hz × 16bit × 1ch = 256,000bps = 32,000 bytes/秒`
- OPUS(現行構成、`bitRate = 24000`のCBR): Opus本体のペイロードは
  `24000bps × 0.02s / 8 = 60バイト/20ms`。これに対しOggのページヘッダ
  (固定27バイト+セグメントテーブル1バイト=28バイト)が乗るため、
  実効は`88バイト/20ms → 4,400 bytes/秒 ≒ 35.2kbps`
- 理論値24kbpsに対し**約47%がOggのコンテナオーバーヘッド**になっている
- LINEAR16からの削減率は現状で**約7.3倍(≒86%減)**

一方で、Google STTでの文字起こし(Text化)のレイテンシも考慮する必要があり、
ローカルでのバッファリングによる追加レイテンシは実用上**100ms程度が上限**と
考えられる。

## Decision

**今回はこのADRとして方針を記録するのみで、実装はまだ行っていない。**
以下の2点の方針を採用する。

### 1. フレーム長を20ms→40msに変更する

Opusが正式にサポートするフレーム長(2.5/5/10/20/40/60ms)の1つである
**40msを単一フレームとしてそのまま使う**。

当初「1パケットに2フレーム分(40ms)を持たせる」という目的で、Opus独自の
マルチフレームパケット機能(TOCバイトの`code 3`によるフレームパッキング)を
検討したが、40ms自体が有効なフレーム長であるため、そちらを使う方が
バイト効率・レイテンシは実質同じままシンプルに実現できる。
マルチフレームパケット機能がAVAudioConverterのOpus実装で実際に
サポートされているかどうかも未検証だったため、そのリスクも回避できる。

### 2. 1 Oggページに2パケット(=80ms分)を格納する

`OggMuxerNode`側でパケットを2個バッファしてから1ページとして出力する
設計に変更する。これによりOggのページヘッダ(27バイト)を2パケット分で
按分できる。

試算:
- Opusペイロード: `120バイト/40ms × 2パケット = 240バイト`
- Oggオーバーヘッド: `27バイト(ヘッダ) + 2バイト(セグメントテーブル、
  パケット2つ分) = 29バイト`
- 合計: `269バイト/80ms → 3,362 bytes/秒 ≒ 26.9kbps`
  (理論値24kbpsに対し**約12%のオーバーヘッド**まで改善)
- LINEAR16比では**約9.5倍(≒89.5%減)**まで改善する見込み

### 3. レイテンシへの影響

追加レイテンシは最大80ms(2パケット目が揃うまでページを送信できないため)。
100msの予算内に収まると判断した。

## Consequences

- 実装時、`OggMuxerNode`は現在「パケットが来るたびに即1ページ出力」という
  単純な設計になっているため、**Nパケット(=2)をバッファしてからページ化する
  ロジックへの変更が必要**になる。
- **flush処理の追加が必須**: 録音停止時に2パケットに満たない端数
  (0または1パケット)が残っていた場合、それを最後のページとして送信する
  flush処理が新たに必要。これを実装しないと、発話の最後の最大40ms分の
  音声が送信されずに失われるバグになる。現状`OggMuxerNode`にはflush用の
  メソッドがなく、[RecordView.swift](../../iOS/google_stt_grpc/google_stt_grpc/RecordView.swift)側でも
  録音停止時に`oggMuxer`へ何も通知していないため、この配線も合わせて
  必要になる。
- `PCMFrameBufferNode`・`OpusEncoderNode`の`frameDurationMs`デフォルト値を
  `20`→`40`に変更するだけで(1)は達成できる見込み(パラメータ化済みのため
  コード変更は小さい)。
- 本ADRの時点では未実装・未検証。実装時は40msフレームでの
  `AVAudioConverter` + `kAudioFormatOpus`の動作確認、および
  Nパケットバッファ+flushを含む`OggMuxerNode`の単体テスト更新が必要になる。
