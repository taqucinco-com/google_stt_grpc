# ADR 2026-09-23: Google STT gRPC適用(Step 3)の実装計画

## Status

Proposed

## Context

[docs/adr/20260920.md](20260920.md) に記録した通り、本プロジェクトは以下の3ステップで
段階的に進めている。

1. 簡単なgRPCサーバーを立てる(`grpc/`) — **DONE**
2. iOS Swift側でgRPC Clientの実装を確立する(`iOS/`) — **DONE**
   ([ContentView.swift](../../iOS/google_stt_grpc/google_stt_grpc/ContentView.swift)、
   [grpc_sample.swift](../../iOS/google_stt_grpc/google_stt_grpc/grpc_sample.swift)で
   unary / server streaming / client streaming / bidirectional streamingの
   4パターンをgrpc-swift 2で実装・動作確認済み)
3. (1)(2)の土台をGoogle STT gRPCに適用する — 本ADRで計画するステップ

Step 3はいきなりGoogle STTに接続すると、UI・録音・エンコード・gRPC送信の
どこに問題があるか切り分けが難しい。そのため要素を1つずつ積み上げて検証する。

## Decision

Step 3を以下の4段階に分割し、この順番で実装・検証していく。

1. **タブ構成の整理**: SwiftUIのbottom navigation(`TabView`)で「home」タブと
   「record」タブの2つを作る。「home」タブには既存のgRPC疎通確認
   (`ContentView.swift`の内容)を残し、「record」タブに以降の録音・送信処理を
   実装していく。既存実装を壊さずに新機能を追加できることを確認する。
2. **録音のbuffering実装**: `AudioQueueEnqueueBuffer`(旧Audio Queue Services)と
   `AVAudioEngine`の2択のうち、実装が簡単な方を選定して録音バッファを取得する
   実装を行う。まずはgRPC送信を挟まず、マイク入力をバッファ単位で取得できることを
   確認する。
3. **非圧縮データでのgRPC送信**: (2)で取得したバッファをエンコードせず、
   そのままバイト列としてgRPC(bidirectional streamingを想定、`SayChat`パターンを
   応用)でサーバーへ送信する。ここではSTTサーバーではなく既存の`grpc/`サーバーを
   使い、音声データが欠落・破損なく届くことの確認を主目的とする。
4. **codec対応の検証**: OPUSなどのcodecでエンコードしたデータをやりとりできるかを
   試す。エンコード/デコードの実装コストと、Google STT streaming APIが受け付ける
   音声フォーマットとの整合性を確認する。

## Consequences

- 各ステップは前段の検証結果に依存する。特に(2)でどちらの録音APIを選ぶかは
  実装の簡単さで決めるため、後段のバッファサイズやフォーマット周りの設計は
  選定結果次第で変わりうる。
- (3)は非圧縮PCMでの疎通確認が目的であり、実際のGoogle STT streaming APIへの
  接続はまだ行わない。プロトコル(proto定義)は`grpc/`側の`Greeter`サービスとは
  別に、音声データ用の新しいサービス/メッセージ定義が必要になる見込みで、
  これは(3)の実装時に別途検討する。
- (4)のcodec選定は、最終的にGoogle STT streaming APIがサポートするエンコーディング
  (例: `LINEAR16`, `OGG_OPUS`など)に合わせる必要がある。本ADRの時点ではOPUSを
  候補として試すに留め、実際にSTTへ繋ぎ込む際に対応フォーマットを再確認する。
- 「home」タブに残す既存実装(unary/server stream/client stream/bidi stream)は
  今後のリグレッション確認の基準として維持する。
