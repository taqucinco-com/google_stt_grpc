# ADR 2026-09-23: Google STT gRPC適用(Step 3)の実装計画

## Status

Accepted

## Context

[docs/adr/20260920.md](20260920.md) に記録した通り、本プロジェクトは以下の3ステップで
段階的に進めている。

1. 簡単なgRPCサーバーを立てる(`grpc/`) — **DONE**
2. iOS Swift側でgRPC Clientの実装を確立する(`iOS/`) — **DONE**
   ([ContentView.swift](../../iOS/google_stt_grpc/google_stt_grpc/ContentView.swift)、
   [grpc_sample.swift](../../iOS/google_stt_grpc/google_stt_grpc/grpc_sample.swift)で
   unary / server streaming / client streaming / bidirectional streamingの
   4パターンをgrpc-swift 2で実装・動作確認済み)
3. (1)(2)の土台をGoogle STT gRPCに適用する — 本ADRで計画するステップ

Step 3はいきなりGoogle STTに接続すると、UI・録音・エンコード・gRPC送信の
どこに問題があるか切り分けが難しい。そのため要素を1つずつ積み上げて検証する。

## Decision

Step 3を以下の4段階に分割し、この順番で実装・検証していく。

1. **タブ構成の整理**: SwiftUIのbottom navigation(`TabView`)で「home」タブと
   「record」タブの2つを作る。「home」タブには既存のgRPC疎通確認
   (`ContentView.swift`の内容)を残し、「record」タブに以降の録音・送信処理を
   実装していく。既存実装を壊さずに新機能を追加できることを確認する。
2. **録音のbuffering実装**: `AudioQueueEnqueueBuffer`(旧Audio Queue Services)と
   `AVAudioEngine`の2択のうち、実装が簡単な方を選定して録音バッファを取得する
   実装を行う。まずはgRPC送信を挟まず、マイク入力をバッファ単位で取得できることを
   確認する。
3. **非圧縮データでのgRPC送信**: (2)で取得したバッファをエンコードせず、
   そのままバイト列としてgRPC(bidirectional streamingを想定、`SayChat`パターンを
   応用)でサーバーへ送信する。ここではSTTサーバーではなく既存の`grpc/`サーバーを
   使い、音声データが欠落・破損なく届くことの確認を主目的とする。
4. **codec対応の検証**: OPUSなどのcodecでエンコードしたデータをやりとりできるかを
   試す。エンコード/デコードの実装コストと、Google STT streaming APIが受け付ける
   音声フォーマットとの整合性を確認する。

## Consequences

- 各ステップは前段の検証結果に依存する。特に(2)でどちらの録音APIを選ぶかは
  実装の簡単さで決めるため、後段のバッファサイズやフォーマット周りの設計は
  選定結果次第で変わりうる。
- (3)は非圧縮PCMでの疎通確認が目的であり、実際のGoogle STT streaming APIへの
  接続はまだ行わない。プロトコル(proto定義)は`grpc/`側の`Greeter`サービスとは
  別に、音声データ用の新しいサービス/メッセージ定義が必要になる見込みで、
  これは(3)の実装時に別途検討する。
- (4)のcodec選定は、最終的にGoogle STT streaming APIがサポートするエンコーディング
  (例: `LINEAR16`, `OGG_OPUS`など)に合わせる必要がある。本ADRの時点ではOPUSを
  候補として試すに留め、実際にSTTへ繋ぎ込む際に対応フォーマットを再確認する。
- 「home」タブに残す既存実装(unary/server stream/client stream/bidi stream)は
  今後のリグレッション確認の基準として維持する。

## 追記: APIキーではなくサービスアカウント+Bearerトークンを使う

ユーザーがGoogle STT用にAPIキーを発行していたため、これがStep 3の認証に
使えるかを調査した。

Google Cloudの認証ドキュメントによると

> 標準のAPIキーはプリンシパル(principal)を認証しない。プリンシパルがないと、
> 呼び出し元が要求された操作を行う権限があるかをIAMでチェックできない

とあり、APIキーは「どのプロジェクトからの呼び出しか」を識別するだけで、
IAMの権限チェックが必要なSpeech-to-Textを単独では認可できない。
Speech-to-Text v1の公式認証ドキュメントにもAPIキーによる認証経路の記載は
一切なく、ADC/サービスアカウント/OAuth2 Bearerトークンのみが案内されている。
gRPCメタデータに`x-api-key`/`x-goog-api-key`としてAPIキーを渡す非公式な
試みも見られるが、動作報告は不安定(Broken Pipeで失敗した例もある)。

REST版の`speech:recognize`(unary、ファイル全体を投げる方式)には歴史的に
`?key=API_KEY`のクイックスタートがあるが、Step 3で使う`StreamingRecognize`は
gRPC限定のbidirectional streamingであり、この経路は使えない。

### Decision

発行済みのAPIキーはREST版での簡易疎通確認用途に留め、gRPC streaming実装の
認証にはサービスアカウント+OAuth2 Bearerトークン方式(後述の`hono/`)を使う。

### Consequences

この判断が、後の「認証トークン発行サーバー(`hono/`)を新設する」ADRの前提と
なっている。

## 追記: iOSソース構成をpackage by featureにする

上記Decisionの1・2を実装した過程で、録音関連のロジックとして以下の2ファイルが
できた。

- [AudioRecorder.swift](../../iOS/google_stt_grpc/google_stt_grpc/Feature/Audio/AudioRecorder.swift)
  — AVAudioEngineでのバッファリングのみを責務とするクラス
- [AudioLevel.swift](../../iOS/google_stt_grpc/google_stt_grpc/Feature/Audio/AudioLevel.swift)
  — AVAudioPCMBufferからdBFS(概算音量)を算出するユーティリティ

この2ファイルは元々`google_stt_grpc/google_stt_grpc/`直下にフラットに
置かれていた。今後gRPC送信・OPUS対応など録音まわりのロジックはさらに
増えていく見込みで、種類別(View/Model/Utilと横断的に分類)にフラットへ
置き続けると機能追跡が難しくなる。

ユーザーの別プロジェクト`ai_golf_check_ios`
(`AiGolfCheck/Feature/Audio/AudioRecorder.swift`等)がpackage by feature
構成(`Feature/<機能名>/`配下に関連ファイルをまとめる)を採用しており、
このリポジトリでも同じ方針を踏襲することにした。

### Decision

- 今後、機能固有のロジック・モデル・ユーティリティ等、複数ファイルに
  またがる実装がまとまるものは`Feature/<機能名>/`ディレクトリに
  まとめる(package by feature)。
- その第一弾として、`AudioLevel.swift`と`AudioRecorder.swift`を
  `google_stt_grpc/google_stt_grpc/Feature/Audio/`へ移動した。
- `ContentView.swift`(TabViewのコンテナ)、`HomeView.swift`、
  `RecordView.swift`はfeature固有のロジックというより画面構成
  (タブのトップレベルView)そのものなので、今回はルート直下
  (`google_stt_grpc/google_stt_grpc/`)に残す。feature配下に切り出すかどうかの
  判断基準は「あるfeature専用のロジックが複数ファイルにまたがってまとまった
  時点」とする。
- このXcodeプロジェクトは`PBXFileSystemSynchronizedRootGroup`
  (Xcode 16以降のfile system synchronized groups)を使っているため、
  `project.pbxproj`を手動編集することなく、ファイルをディレクトリへ
  移動するだけでXcodeが自動的に認識する。

#### 確認したコマンド

```bash

$ xcodebuild -project google_stt_grpc.xcodeproj -scheme google_stt_grpc \
    -destination 'generic/platform=iOS Simulator' build

```

### Consequences

- 今後Step 3のstep3(非圧縮データでのgRPC送信)やstep4(OPUS等codec対応)で
  増える録音関連ロジックも、同様に`Feature/Audio/`配下に追加していく想定。
- file system synchronized groupsのおかげで、ディレクトリ移動によるリファクタは
  `project.pbxproj`のコンフリクトを気にせず低コストで行える。
- 画面(View)そのものをどこまでfeature配下に含めるかは今回明確な基準を
  決め切っていない(現状はルート直下のまま)。featureが増えて
  `ContentView`/`HomeView`/`RecordView`がそれぞれ肥大化した場合は、
  View自体もfeature配下へ移すかどうかを別途検討する。

## 追記: 認証トークン発行サーバー(`hono/`)を新設する

Step 3でiOSからGoogle STTのgRPCへ接続するには`authorization: Bearer <アクセストークン>`
が必要になる(詳細は[README.md](../../README.md#google-cloud-speech-to-text-stt-grpc-api)
参照)。このトークンはサービスアカウントの秘密鍵から発行するものだが、
Google Cloudの公式ベストプラクティスは以下を明言している。

> クライアントサイドのアプリケーション(ツール、デスクトッププログラム、
> モバイルアプリなど)では、サービスアカウントを使用しないでください

秘密鍵をモバイルアプリのバイナリに同梱するとリバースエンジニアリングで
抽出されうるため、モバイルアプリ単体でアクセストークンを安全に発行する方法は
存在しない。この問題への対処方針として、以下の2案を検討した。

1. **トークン発行のみを代行するバックエンドを新設する**: 秘密鍵はサーバー側だけが
   持ち、短命なアクセストークンの発行のみを行う。iOSはそのトークンを使って
   `speech.googleapis.com`と直接gRPCで話す。
2. **バックエンドがGoogle STTへの通信を丸ごと中継する(フルプロキシ)**: iOSは
   既存の`grpc/`サーバーとだけ話し、`grpc/`サーバーが内部でGoogle STTへの
   認証・gRPC呼び出し・レスポンス中継を行う。

### Decision

**1(トークン発行のみを代行)を採用する。** 条件として、以下を満たす。

- **Goでは実装しない**。既存の`grpc/`(Go)とは別に新設する。
- フレームワークは**Hono**を使う。Nest.jsも候補だったが、この責務は
  「サービスアカウントの認証情報から`google-auth-library`でアクセストークンを
  発行してJSONで返す」という単一エンドポイントのみであり、DI・モジュールを
  前提としたNest.jsの構成を組むほどの規模ではないため、薄いルーティング層
  のみのHonoを選定した。
- ディレクトリは`hono/`とする(リポジトリルート直下、`grpc/`・`iOS/`と並ぶ構成)。
- **Dockerで起動し、ローカル環境でも使えること**。`docker-compose.yml`に
  `grpc`サービスと並ぶ形で追加する想定。
- サービスアカウントの認証情報は`.env`経由で渡し、リポジトリにはコミットしない
  (AGENTS.mdの「注意事項」を参照)。

2(フルプロキシ)を採らなかった理由は、今回はあくまで「トークン発行のみを
代行する」という条件で合意したため。フルプロキシの方がiOS側の責務
(トークン有効期限管理・再取得)を減らせるという利点は認識しつつ、
まずはシンプルな1で進める。

#### 作成手順

[Hono公式のNode.js向けセットアップ](https://hono.dev/docs/getting-started/nodejs)
に従い、対話プロンプトを避けるため`--template`/`--pm`/`--install`を指定して
リポジトリルートで`hono/`をscaffoldした。

```bash
$ npm create hono@latest hono -- --template nodejs --pm npm --install
```

生成された`hono/src/index.ts`のデフォルト実装(`GET /`で`"Hello Hono!"`を返す
だけ)に対し、ポートを`3000`→`8787`、レスポンス文言を`"hello, hono!"`に変更。
`grpc/Dockerfile`と同じ「ビルドせずdevスクリプトをそのまま動かす」方針で
[hono/Dockerfile](../../hono/Dockerfile)を作成し、`docker-compose.yml`に
`grpc`と並ぶ`hono`サービスを追加した(`node_modules`はホストとコンテナの
差異を避けるため anonymous volume でコンテナ側を優先させている)。

```bash
$ docker compose up -d --build hono
$ curl -s http://localhost:8787/
hello, hono!
```

#### `/token`エンドポイントの実装

[google-auth-library](https://github.com/googleapis/google-auth-library-nodejs)の
`GoogleAuth`(スコープ`https://www.googleapis.com/auth/cloud-platform`)で
`GET /token`がアクセストークンをJSONで返す実装を追加した
([hono/src/index.ts](../../hono/src/index.ts))。

`GoogleAuth`はADC(Application Default Credentials)の探索順に従い、
`GOOGLE_APPLICATION_CREDENTIALS`環境変数が指すJSONキーファイルを読む。
サービスアカウントの秘密鍵は`hono/secrets/service-account.json`
(`.gitkeep`以外gitignore済み)に置く運用とし、`./hono:/usr/src/app`の
bind mountでコンテナ内にもそのまま見えるようにした。
`docker-compose.yml`の`hono`サービスに

```yaml
environment:
  - GOOGLE_APPLICATION_CREDENTIALS=/usr/src/app/secrets/service-account.json
```

を追加。付与するIAMロールは呼び出し専用の最小権限である
`roles/speech.client`を想定([Speech-to-Text roles and
permissions](https://docs.cloud.google.com/iam/docs/roles-permissions/speech))。

キー未配置の状態で意図通りエラーになることを確認済み:

```bash
$ curl -s -i http://localhost:8787/token
HTTP/1.1 500 Internal Server Error
{"error":"failed to issue access token"}
```

実際にサービスアカウントを作成し(`roles/speech.client`付与、Speech-to-Text API
有効化)、`hono/secrets/service-account.json`にJSONキーを配置した状態で
動作確認済み:

```bash
$ docker compose up -d --build hono
$ curl -s -o /tmp/token_response.json -w "HTTP %{http_code}\n" http://localhost:8787/token
HTTP 200
```

`ya29.`で始まる実際のGoogle OAuth2アクセストークンが返ることを確認した
(トークン値そのものは秘匿情報なのでログ・ドキュメントには残さない)。

なお、サービスアカウントの秘密鍵を直接使う自己署名JWTでのトークン発行には
`roles/iam.serviceAccountTokenCreator`のような追加権限は不要
(秘密鍵の所持自体がトークン発行の権限になるため。このロールが必要なのは
秘密鍵を持たずになりすまし=impersonationでトークンを発行する場合のみ)。

#### トークンの生存期間

`getAccessToken()`自体は`token`しか返さないため、有効期限は副作用で
更新される`client.credentials.expiry_date`(epoch ms)から算出するよう
`/token`のレスポンスに`expires_in`(秒)を追加した。

Googleのサービスアカウントアクセストークンはデフォルトで最大1時間
(3600秒)が有効期限。実際に発行して確認したところ`expires_in: 3599`
(≒3600秒)だった。組織ポリシー
(`constraints/iam.allowServiceAccountCredentialLifetimeExtension`)で
最大12時間まで延長可能だが、今回は特に設定していないのでデフォルトの
1時間のまま。

```bash
$ curl -s http://localhost:8787/token
{"access_token":"ya29.c.c0AZ4...","expires_in":3599}
```

#### トークンの有効性そのものの検証

`/token`の返り値が本当にGoogleに通用するかを、Google自身の検証エンドポイント
`https://oauth2.googleapis.com/tokeninfo`に投げて確認した:

```bash
$ curl -s "https://oauth2.googleapis.com/tokeninfo?access_token=${TOKEN}"
{"scope":"https://www.googleapis.com/auth/cloud-platform","expires_in":3599,"access_type":"online"}
```

`HTTP 200`、`scope`が要求した`cloud-platform`と一致、`expires_in`も`/token`の
レスポンスと一致した。`hono`が発行しているのがGoogle自身が正当と認める
本物のアクセストークンであることを確認できた。

### Consequences

- iOSアプリ側はアクセストークンの有効期限管理・失効時の再取得ロジックを
  自前で持つ必要がある(2のフルプロキシ方式なら不要だった責務)。
  `expires_in`(デフォルト約1時間)を見て、期限が近づいたら`/token`を
  再度叩き直す実装になる見込み。
- `hono/`サーバーのエンドポイント形状(REST GET・
  `{"access_token": "...", "expires_in": ...}`)は決定し、実サービス
  アカウントキーでの動作確認も完了した。
- 将来的にトークン発行以外の責務(例: フルプロキシへの移行)が必要になった
  場合、Honoのままスケールさせるか、Nest.js等より構造化されたフレームワークへ
  移行するかは、その時点の要件次第で再検討する。

## 追記: Step 3のstep3を「自前grpc/サーバー経由」からGoogle STT直接接続へ変更する

当初のDecisionのstep3は「既存の`grpc/`サーバーへ非圧縮データを送り、データ
整合性を確認する」というものだった。実際に`grpc/audio/audio.proto`
(`AudioIngest.StreamAudio`)を実装し、`grpcurl`で送信バイト数とサーバー側の
`receivedBytes`が一致することを確認、iOS側もAVAudioEngineのバッファを
`AVAudioConverter`でLINEAR16に変換して送信できることまで確認できた。

しかしこの時点で「認証トークン発行サーバー(`hono/`)」が既に完成しており、
Google STTへ直接繋ぐための材料(録音バッファ・LINEAR16変換・アクセストークン)が
揃っていた。自前`grpc/`サーバーを経由する中間ステップを維持する意味が薄れたため、
**Google STTに直接接続する方針に変更**した。

### Decision

- iOS(`Feature/Audio/SpeechStreamClient.swift`)から`speech.googleapis.com:443`へ
  TLS接続し、`google.cloud.speech.v1.Speech.StreamingRecognize`を直接叩く。
- 検証用に実装した`grpc/audio/audio.proto`・生成コード・`main.go`の
  `audioIngestServer`、iOS側の`gRPC/audio.proto`・`AudioStreamClient.swift`は
  すべて削除した(不要になったため)。`grpc/`は`greeter.Greeter`のみの状態に戻した。
- Google STT v1のprotoは[googleapis/googleapis](https://github.com/googleapis/googleapis/blob/master/google/cloud/speech/v1/cloud_speech.proto)
  で公開されているが、`google/api/*`・`google/longrunning/operations.proto`・
  `google/rpc/status.proto`等の外部importに依存しており、そのままではコンパイル
  できない。今回は`StreamingRecognize`に必要な最小限のメッセージだけを抜粋し、
  外部importを一切持たない自己完結型のprotoを作成した
  ([gRPC/speech.proto](../../iOS/google_stt_grpc/google_stt_grpc/gRPC/speech.proto))。
  **package名・service名・method名・使用するフィールドの番号は本家と完全に
  一致させている**ため、宣言していないフィールド(`error`, `speech_event_type`等)
  はprotobufの「未知フィールドは読み飛ばす」性質によりワイヤー互換性を保ったまま
  安全に省略できる。
- 認証は`ClientInterceptor`(grpc-swift 2)で実装した。`intercept`のたびに
  `hono`の`/token`からアクセストークンを取得し、`authorization: Bearer <token>`
  をリクエストのmetadataに注入する
  ([SpeechStreamClient.swift](../../iOS/google_stt_grpc/google_stt_grpc/Feature/Audio/SpeechStreamClient.swift))。
- TLSは`transportSecurity: .tls`(デフォルト設定、システム信頼のCA)を使用。
  `grpc/`向けの`.plaintext`とは別経路。

### 実装時にローカルのSPMソースで確認したgrpc-swift 2特有のAPI

ドキュメントの検索結果だけでは正確なシグネチャが分からなかったため、
`~/Library/Developer/Xcode/DerivedData/.../SourcePackages/checkouts/grpc-swift-2`
配下の実際のソースを読んで確認した。

- `ClientInterceptor.intercept`の`next`クロージャ引数には`@concurrent`属性が
  必要(このプロジェクトの`SWIFT_APPROACHABLE_CONCURRENCY`設定に起因)。
  付けないと「type does not conform to protocol」というやや分かりにくい
  エラーになる。
- `Metadata`への値の追加は`request.metadata["key"] = value`のような
  subscript代入ではできず、`request.metadata.addString(_:forKey:)`を使う。
- `TransportSecurity.tls`(スタティックプロパティ)でデフォルト設定のTLSが
  使える。

### 動作確認

- Go側: `grpc/audio/audio.proto`削除後、`go build`/`go vet`/Docker起動/
  `grpcurl -plaintext localhost:50051 list`で`greeter.Greeter`のみになった
  ことを確認済み。
- iOS側: `xcodebuild`は成功。**実際にXcodeから実行し、`hono`経由で取得した
  トークンでGoogle STTのStreamingRecognizeに接続、マイク入力の文字起こし結果が
  RecordView上に表示されることをユーザーが実機で確認済み。**

### Consequences

- Step 3は当初計画の4段階(タブ整理→バッファリング→自前サーバーでの疎通確認→
  codec検証)のうち、3段階目を「自前サーバー経由の疎通確認」から「Google STT
  直接接続」に置き換える形で完了した。`grpc/`は今後Google STT関連では使わない
  (Greeterのサンプル疎通確認用としては引き続き残す)。
- 残るのはStep 3のstep4(OPUS等codecの検証)。現在はLINEAR16(非圧縮)のみで
  接続できている状態。
- `speech.proto`は必要最小限のサブセットなので、今後`single_utterance`や
  `speech_event_type`等、省略したフィールドを使いたくなった場合は本家protoを
  見ながら該当フィールドをこのファイルに追記する運用になる。

## 追記: `greeter`をサーバーレスで配信するならCloud Run(将来検討用のメモ)

`grpc/`(`greeter.Greeter`、bidirectional streamingの`SayChat`含む)を将来
サーバーレスで配信したくなった場合にどの選択肢が現実的かを調査した。
**今すぐ実装するものではなく、将来判断するための調査記録**。

### 調査結果

- **AWS Lambda(従来型)**: gRPCとの相性が悪い。LambdaはHTTP/2の永続接続では
  なく1リクエスト=1回のイベント起動モデルであり、API GatewayはgRPC trailers
  非対応、ALB経由でLambdaをターゲットにしてもLambdaのレスポンスストリーミングは
  gRPCのフレーミング・trailers・クライアントストリーミングを提供しない。
  bidirectional streaming(`SayChat`相当)は事実上実装できない。
- **AWS Lambda MicroVMs(2026年6月GA)**: 従来のLambdaとは別の新プリミティブ。
  Firecracker microVMごとに専用HTTPSエンドポイントを持ち、HTTP/2・gRPC・
  WebSocket・SSEをネイティブサポートする(最大8時間起動維持、Bearerトークン
  認証)。技術的にはbidirectional streamingを含む本物のgRPCサーバーを
  動かせる見込みだが、想定用途はAIエージェントのサンドボックス実行であり、
  常時稼働のマイクロサービスホスティングとしての実績はまだ薄い。
- **Google Cloud Run**: 2021年からHTTP/2エンドツーエンド・gRPC
  bidirectional streamingを正式サポートしている、実績のある選択肢。
  `grpc/`は既にDocker化されているため、`PORT`環境変数でリッスンするよう
  修正する程度でほぼそのままデプロイできる(現状plaintextでリッスンしている
  点もCloud RunがエッジでTLS終端する構成とそのまま噛み合う)。

  ```bash
  gcloud builds submit --tag <REGION>-docker.pkg.dev/<PROJECT>/<REPO>/grpc
  gcloud run deploy grpc --image <REGION>-docker.pkg.dev/<PROJECT>/<REPO>/grpc --use-http2
  ```

  制約: リクエストタイムアウトがストリーム全体に適用される
  (デフォルト5分、最大60分)。

### Decision

**今のところ実装しない(調査のみ)。** 仮に`greeter`をサーバーレスで配信する
ことになった場合は、Google Cloud Runを第一候補とする。理由は
(1) bidirectional streamingを含むgRPCサポートが成熟していること、
(2) このプロジェクトが既にGoogle Cloud(STT、サービスアカウント)に
依存しており構成が揃っていること、(3) 既存のDockerfileをほぼそのまま
使い回せること。

AWS Lambda MicroVMsは2026年6月GAの新機能で、gRPCネイティブ対応という
特性上このユースケースにも将来使える可能性があるため、**動向を継続的に
ウォッチする対象**とする(現時点では採用しない)。

### Consequences

- `grpc/`のサーバーレス配信は現時点では未着手・未計画。将来必要になった際は
  本追記を起点にCloud Runでの実装を検討する。
- AWS Lambda MicroVMsが成熟し、常時稼働マイクロサービスのホスティングとして
  実績が積まれた場合は、再度比較検討の余地がある。

## 追記: Step 3のstep4(OPUS対応)をノードパイプラインで実装する

Step 3の最後のサブステップである「OPUSなどのcodecでエンコードしたデータを
やりとりできるかを試す」を実装した過程の記録。

### 設計: AudioPipelineNodeによるノード接続

音声処理を1つの関数に詰め込むのではなく、AudioUnitのnode接続のように
「入力を受け取り、0回以上`onOutput`へpushする」という契約
(`Feature/Audio/AudioPipelineNode.swift`)を定義し、各処理を独立したノードに
分割した。

```swift
protocol AudioPipelineNode: AnyObject {
  associatedtype Input
  associatedtype Output
  var onOutput: ((Output) -> Void)? { get set }
  func process(_ input: Input)
}
```

`onOutput`は`process`の引数ではなく、接続時に1回だけ設定するプロパティにした
(`connect(to:)`ヘルパーで配線する)。これにより、`process`呼び出しのたびに
コールバックをネストして渡す必要がなくなった。

途中で`PCMBufferSerializer`・`PCMFormatConverter`・`PCMFrameBuffer`の3ファイルに
`Node`サフィックスを付け、`Feature/Audio/Node/`ディレクトリへ移動した
(命名・配置の一貫性のため)。

### 音声パイプラインの構成

```
生のAVAudioPCMBuffer(ネイティブフォーマット)
  → PCMFrameBufferNode   (固定フレーム長に整形。AVAudioPCMBuffer→AVAudioPCMBuffer)
  → OpusEncoderNode        (AVAudioConverter+kAudioFormatOpus。AVAudioPCMBuffer→AVAudioCompressedBuffer)
  → OggMuxerNode           (Ogg Opusコンテナ化。AVAudioCompressedBuffer→Data)
  → speechStream.send(data)
```

設計上の方針として、**AVFoundationのネイティブ型(`AVAudioPCMBuffer`/
`AVAudioCompressedBuffer`)はできるだけ後段まで崩さず、実際にバイト列が
必要になる最後の段(`OggMuxerNode`)でのみ`Data`化する**ことにした。
当初`OpusEncoderNode`の出力を`Data`にしていたが、`AVAudioCompressedBuffer`の
まま扱う方が構造を保てるため差し替えた(`OggMuxerNode`側でバイト列を取り出す
形に変更)。

- `PCMFrameBufferNode`: CoreAudioの`installTap`が返すバッファサイズは
  リクエストであって保証ではない(Appleの公式ドキュメントに明記されている)
  ため、フレーム境界をまたいだ端数を内部に保持し、次回の`process`呼び出しで
  結合する。サンプル型(Int16/Float32)に依存しないよう、`AudioBufferList`の
  生バイトを`memcpy`する実装にした。
- `OpusEncoderNode`: `AVAudioConverter` + `kAudioFormatOpus`(iOS 11〜)で
  AVFoundationのみで完結する。48kHz固定、`AVAudioBitRateStrategy_Constant`。
  Appleエンジニアが2024年12月にフォーラムで提示した動作例
  ([thread 763362](https://developer.apple.com/forums/thread/763362))を
  参考にした。
- `OggMuxerNode`: 既存のSwiftライブラリ(`swift-ogg`はファイル全体変換専用で
  libopus/libogg両方を内包、`ybrid/ogg-swift`はドキュメント不足・保守状況
  不透明)がどちらも要件に合わず、RFC 3533(Ogg)・RFC 7845(Ogg Opus)に基づき
  自前実装した。単一ストリーム・1パケット1ページの最小実装。

### 単体テスト

Swift Testingフレームワークで、440Hzのサイン波を入力とするテストを追加した
(`google_stt_grpcTests/`)。

- `PCMFrameBufferNodeTests`: フレーム長(960サンプル)の倍数にならない
  チャンクで入力し、連結した出力が元の連続したサイン波と完全一致すること
  (欠落・重複なし)を検証。
- `OpusEncoderNodeTests`: 実際にエンコードし、非空・仕様上限(1275バイト)
  以内のパケットが出ることを確認。さらに`AVAudioConverter`で組んだデコーダで
  ラウンドトリップし、ゼロクロス法で440Hz付近の周波数が保たれていることを確認。
- `OggMuxerNodeTests`: 実際のOpusパケットを3個流し、`OpusHead`(BOS)+
  `OpusTags`+音声ページ3枚の計5ページ、ページ番号の連番、granule positionの
  増分、CRC32の自己整合性を検証。

### 発見: Opusのアルゴリズム遅延(algorithmic delay)

`OpusEncoderNodeTests`のラウンドトリップテストで、960サンプルのフレームを
エンコード→デコードすると、デコード結果が960ではなく840サンプルになる
現象を発見した。

原因はOpus(CELTレイヤー)のMDCT(overlap-add変換)に起因する**アルゴリズム
遅延**。RFC 6716によると

> CELTレイヤーの基本的な2.5msの先読みは、エンコーダ側で削減できない。
> これはMDCTのoverlapに必要なもので、そのサイズはデコーダ側で固定されている

CELTの基本先読みは2.5ms = 48kHzで120サンプル。`960 - 840 = 120`と一致する。
単発の1パケットだけを孤立してエンコード→デコードしたため、本来前のフレームの
終端と合成されるべきoverlap-add分(120サンプル)が欠けた状態で出てきたと
考えられる。

RFC 7845(Ogg Opus)はこれに対処するため`OpusHead`に`pre-skip`フィールドを
持たせており、本来は`OPUS_GET_LOOKAHEAD`相当の値(概ね120サンプル程度)を
設定すべきとされている。現在の`OggMuxerNode.makeOpusHead()`は`pre-skip`を
`0`固定にしている。

### Consequences

- テストは固定フレーム長を仮定せず、実際のデコード結果の長さから周波数を
  推定する頑健な実装にした(アルゴリズム遅延の影響を受けない)。
- `pre-skip=0`固定は、本来のOgg Opus仕様としては不正確(正しくは
  `OPUS_GET_LOOKAHEAD`相当の値を設定すべき)だが、Google STTは再生タイミング
  ではなく文字起こし精度が目的のため、実用上の影響は小さいと判断し、
  現時点では修正していない。将来的に正確な値を設定する場合は、
  `AVAudioConverter`がlookahead値を直接公開していないため、CELTの
  基本先読み(2.5ms=120サンプル@48kHz)を固定値として使うなどの対応が必要。
- まだ`RecordView`にはOpusパイプラインを接続していない(既存のLINEAR16
  パイプラインは無傷)。次のステップはRecordViewへの接続と、
  `RecognitionConfig.encoding`を`OGG_OPUS`に切り替えての実機確認。
